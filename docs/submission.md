# 인증 구현 설명서

## ① 무엇으로 붙였나

- **방식: 프레임워크 내장 인증 + 직접 쓴 화면·소유자 확인.** 인증 서비스(외부 로그인 서비스)는 쓰지 않았습니다.
- **Django 6.1.1**의 `django.contrib.auth`(가입 계정 모델, 비밀번호 해시, 로그인·로그아웃, 세션)를 씁니다. 함께 쓴 패키지: gunicorn 26.2.0, whitenoise 6.12.0, dj-database-url 3.1.2, psycopg2-binary 2.9.13.
- **비밀번호 해시:** PBKDF2-SHA256, 반복 1,500,000회, 계정마다 다른 소금값(Django가 자동으로 붙임). 비밀번호를 다루는 부분은 Django에 맡겼고 직접 만든 해시 코드는 없습니다.
- **사람 알아보는 방식:** 서버 세션. 서버 DB에 세션을 저장하고 브라우저에는 무작위 세션 ID 쿠키(HttpOnly)만 줍니다. 만료는 24시간입니다.
- **직접 쓴 부분:** 가입·로그인·로그아웃 화면 처리(`diary/views.py`), JSON API의 로그인 확인과 소유자 확인(`diary/api.py`).
- **저장:** 서버 DB(배포는 PostgreSQL, 로컬은 SQLite). 브라우저에는 자료나 토큰을 저장하지 않습니다(localStorage·sessionStorage 미사용).

## ② 왜 그걸 골랐나

- 한 문장(초안): `[내 말로 고치기]` 비밀번호 해시와 세션처럼 실수하기 쉬운 부분을 널리 쓰이는 프레임워크에 맡기고, 제가 직접 쓰는 코드는 "남의 자료가 안 열리게 하는 부분"에 집중하려고 Django 내장 인증을 골랐습니다.
- **함께 검토했지만 고르지 않은 방법**
  - *Supabase Auth(인증 서비스):* 비밀번호·세션을 서비스가 처리해 편하지만, 이번 과제가 요구하는 "소스의 어디를 고쳤나"와 로그아웃 뒤 거절을 내 코드로 보이기 어려워 고르지 않았습니다.
  - *JWT 직접 구현:* 로그아웃한 뒤에도 만료 전까지 서버가 토큰을 쉽게 끊지 못해 "로그아웃 뒤 거절"을 증명하기 불리하고, 비밀키 관리 부담도 커서 서버 세션을 골랐습니다.
- 남이 만든 것을 쓴 것은 감점이 아니며, 직접 만든 해시·암호 코드는 없다는 점을 명시합니다.

## ③ 어디를 어떻게 고쳤나

6번 다이어리는 로그인 없이 링크를 아는 누구나 보는 **단일 HTML 파일**이었고, 자료는 공유 저장소에 있었습니다. 이번에는 서버(Django)와 DB로 옮기고, 모든 자료 요청이 서버에서 주인을 확인하도록 바꿨습니다. 6번의 첫 화면 경고문("링크를 아는 사람은 누구나 볼 수 있습니다")은 더는 사실이 아니라서 없앴고, 첫 화면은 로그인 화면입니다.

### 네 흐름이 소스의 어디를 지나는가

| 흐름 | 화면/주소 | 소스 위치(함수) |
|---|---|---|
| **가입** | `/signup/` | `config/urls.py` → `diary/views.py` `signup_view`(50행~): 아이디 형식·중복 확인(소문자로 통일) → 비밀번호 규칙 확인(`config/settings.py` `AUTH_PASSWORD_VALIDATORS`) → `User.objects.create_user`(71행, PBKDF2로 해시 저장, 설정 81행) → `login`(75행) |
| **로그인** | `/login/` | `diary/views.py` `login_view`(34행~): `authenticate`(40행) 성공 시 `login`(42행, 세션 키 새로 발급, 서버 DB에 세션 저장 · 설정 89~93행) / 실패 시 `LOGIN_FAIL`(20행, 아이디 없음·비밀번호 틀림 똑같은 문구)을 401로 |
| **로그아웃** | `/logout/` (POST만) | `diary/views.py` `logout_view`(81행~): `logout(request)`(82행)가 서버의 세션 행을 지움 |
| **자료 조회** | 화면 `/app/` · 목록 `/api/data/` · 한 건 `/api/todos/<번호>/` 등 | 화면: `app_view`(87행)가 로그인 아니면 `/login/`으로 이동. API: `diary/api.py` `require_login`(42행)이 로그인 아니면 401 → 목록은 `collect`(224행)가 항상 `filter(owner=user)` → 한 건·수정·삭제는 `owned_or_404`(82행~88행)가 `owner=request.user` 조건으로만 찾고 없으면 404 |

### 남의 자료를 막는 위치

- 한 곳(`owned_or_404`, `diary/api.py` 82행)에서 "내 것이 아니면 없는 것과 똑같이 404"로 답합니다. 그래서 남의 자료가 존재하는지도 알 수 없습니다.
- 목록은 별도 경로라서 따로 `owner=user` 조건을 겁니다(`collect` 224행, `export_view` 243행).
- 주소·헤더·본문에 `owner`, `user_id` 등을 적어 보내도 읽지 않습니다. 저장할 때 주인은 항상 로그인한 사람(`owner=request.user`)입니다.
- 순서 바꾸기(`reorder`, 362행)는 내 것이 아닌 번호가 하나라도 섞이면 아무것도 바꾸지 않고 통째로 거절합니다.
- 완료 연타(`todo_complete`, 439행)는 "진행 중인 것만 완료로 바꾸는" UPDATE 한 문장이라 몇 번을 눌러도 완료는 한 번입니다. 실행 기록은 요청마다 붙는 열쇠(`requestId`)와 DB 유일 제약으로 같은 요청이 여러 번 와도 한 건만 남습니다(`record_create`, 471행).

### 비밀값을 어디에 두는가

- 비밀키는 환경변수 `DJANGO_SECRET_KEY`로만 받습니다(`config/settings.py` 20행). 없으면 배포 모드에서는 서버가 아예 뜨지 않습니다(26행). 개발 모드의 임시 키는 실행할 때마다 새로 만들고 어디에도 저장하지 않습니다.
- Render 배포에서는 비밀키를 Render가 만들어 환경변수로 넣습니다(`render.yaml`의 `generateValue`). 소스·Git·브라우저 코드에 키 원문이 없습니다.
- 서버 로그는 메서드·경로·상태코드만 남기고 본문·쿠키·헤더는 읽지 않습니다(`diary/middleware.py`).

## ④ 안 열리는 것을 확인한 기록

모든 요청과 응답 원문(쿠키·토큰·비밀번호는 가림)은 [`docs/evidence.md`](evidence.md)에 있습니다. `python3 scripts/verify_auth.py`가 임시 DB와 일회용 비밀키로 서버를 띄워 실제로 보내고 받은 것입니다. 60개 확인이 모두 통과했습니다.

확인 다섯 가지의 **성공한 요청과 거절된 요청**(같은 주소·같은 방식, 달라진 것은 로그인/로그아웃 또는 자료의 주인뿐):

| # | 확인 | 성공한 요청 | 거절된 요청 |
|---|---|---|---|
| 1 | 로그인 없이 자료 화면 열기 | 로그인한 상태 `GET /app/` → **200** | 로그인 안 한 상태 `GET /app/` → **302** `/login/?next=/app/` (자료 API `GET /api/data/`는 **401** `{"detail": "로그인이 필요합니다."}`) |
| 2 | 로그아웃 뒤 같은 값으로 요청 | 로그아웃 전 `GET /api/me/` (같은 세션 쿠키 `sess…생략`) → **200** | 로그아웃 뒤 복사해 둔 같은 쿠키로 `GET /api/me/` → **401** (서버의 세션 행도 1건 → 0건으로 사라짐) |
| 3 | 남의 자료 **읽기** (양방향) | A가 자기 할 일 `GET /api/todos/1/` → **200** / B가 자기 할 일 `GET /api/todos/3/` → **200** | A가 B의 `GET /api/todos/3/` → **404** / B가 A의 `GET /api/todos/1/` → **404** (계획·실행 기록 읽기도 모두 404) |
| 4 | 남의 자료 **수정** (양방향) | A가 자기 할 일 `PUT /api/todos/2/` → **200** / B가 자기 할 일 `PUT /api/todos/4/` → **200** | A가 B의 `PUT /api/todos/3/` → **404** / B가 A의 `PUT /api/todos/1/` → **404** (계획 수정도 404) |
| 5 | 남의 자료 **삭제** (양방향) | A가 자기 할 일 `DELETE /api/todos/5/` → **200** / B가 자기 할 일 `DELETE /api/todos/6/` → **200** | A가 B의 `DELETE /api/todos/3/` → **404** / B가 A의 `DELETE /api/todos/1/` → **404** (계획·실행 기록 삭제도 404) |

거절 응답은 모두 `{"detail": "찾을 수 없습니다."}`로, 존재하지 않는 번호를 요청했을 때의 응답과 같습니다(존재 자체를 감춤).

추가로 확인한 것(모두 `docs/evidence.md`에 요청·응답이 있음):

- **계정 두 개를 만들어 각각에 자료**(계획 2·할 일 2·실행 기록 1)를 넣었습니다. 비밀번호는 적지 않습니다.
- **거절 앞뒤 건수:** A가 B를 건드리기 전후로 B의 자료 건수·제목이 같고, 반대 방향도 같습니다. 거절 때문에 반대편에 새로 생긴 자료가 없습니다.
- **주소·헤더·본문에 다른 계정을 적어 보내기:** 본문에 `owner`·`user`·`username`·`user_id`, 헤더에 `X-User-Id`·`X-Owner`·`X-Account`, 주소에 `?owner=…&user=…`를 적어도 만들어진 자료의 주인은 로그인한 A였고, 목록에는 A의 자료만 돌아왔습니다. 목록 응답 전체에 B의 자료가 하나도 없습니다.
- **로그인 없는 직접 요청:** 목록·한 건 읽기·삭제 모두 **401**이며 응답에 자료가 없습니다.
- **비밀번호가 저장된 모습**(`auth_user.password`): `알고리즘$반복횟수$소금값$해시` 모양(`pbkdf2_sha256$1500000$소금값 앞 6글자…생략$해시 앞 6글자…생략`)이고 입력한 글자가 보이지 않습니다. **같은 비밀번호로 만든 두 계정**의 저장값은 소금값부터 달라 서로 다릅니다. 두 계정의 실제 저장 모습은 `docs/evidence.md`의 "카드 2"에 있습니다(소금값·해시는 매번 새로 만들어지는 값이라 이 문서에는 옮겨 적지 않았습니다).
- **로그·화면·응답에 비밀번호 원문 없음:** 서버 로그, 화면(HTML), 정적 파일(app.js), API 응답, 오류 화면 어디에도 비밀번호·비밀키 원문이 없습니다.
- **세션:** 쿠키에 `Max-Age=86400`(24시간)과 `HttpOnly`가 붙고, 세션 값은 주소(URL)에 실려 다니지 않습니다(실제로 보낸 모든 요청 주소를 서버가 발급한 쿠키 값과 대조). 비밀번호를 바꾸면 다른 기기에서 로그인해 둔 세션이 **401**로 끊깁니다.
- **같은 아이디로 두 번 가입:** 막힙니다(대소문자만 다른 아이디도). **아이디가 없을 때와 비밀번호만 틀릴 때**는 똑같은 문구·401입니다.
- **비밀키가 새지 않았는지:** 작업 폴더 전체, Git 기록 전체, 화면·API 응답·서버 로그에 일회용 비밀키 원문이 없고, 소스에 비밀키를 문자열로 박아 둔 곳이 없습니다.
- **연타·중복:** 완료 요청 8번을 동시에 보내도 완료 시각은 1종류, 같은 실행 기록 요청 6번을 동시에 보내도 DB에 1건입니다.
- **내보내기·계정 삭제:** 내 자료 전체가 JSON 파일 하나로 내보내지고(비밀번호 정보 없음), 틀린 비밀번호로는 계정 삭제가 거절(400)됩니다. 올바른 비밀번호로 지우면 계정과 자료가 함께 사라집니다(화면에도 "함께 영구 삭제" 안내가 있습니다).

**검증 과정에서 있었던 일(숨기지 않고 적습니다):** 처음 돌렸을 때 60개 중 2개가 실패했습니다. 원인은 서비스가 아니라 검증 스크립트의 오탐이었습니다(요청 기록 블록 안의 `Cookie:` 줄을 주소로 읽음, 스크립트 자신의 변수 줄을 비밀키로 오인). 검사 방식을 "실제 요청 주소 ↔ 서버가 발급한 쿠키 값 직접 비교"로 고쳤고, 서비스 코드는 그 때문에 바꾸지 않았습니다. 한편 확인 다섯 번째 쌍에 필요한 "내 자료 삭제 성공" 요청이 기록에 빠져 있던 것을 발견해 스크립트에 추가했습니다.

## ⑤ AI와 나

- **AI에게 맡긴 일:** Django 프로젝트 코드(가입·로그인·로그아웃, API, 소유자 확인), 화면 코드, 검증 스크립트와 단위 테스트, 이 설명서 초안 작성, 실제 요청을 보내 응답 기록 만들기.
- **내가 직접 판단한 일:** `[직접 작성]` 예) 선택지 비교표를 보고 조합 A(Django + 서버 세션 + PBKDF2 + Render)를 고른 것, 5일 실험의 질문·지표·단위·계획 규칙을 정한 것, ⑥에 적은 못 막은 것을 확인하고 더하거나 뺀 것, 배포와 최종 확인.
- **AI 제안을 따르지 않은 일:** `[직접 작성]` 실제로 있었다면 적고, 없다면 왜 없었는지(예: 제안이 요구사항과 맞아서 모두 따랐다) 이유를 적습니다. 지어서 적지 않습니다.

## ⑥ 아직 못 막은 것 (그리고 왜 위험한가)

1. **무차별 대입(비밀번호를 계속 바꿔 가며 시도) — 못 막았습니다.** 로그인 시도 횟수 제한이나 계정 잠금이 없습니다. 8자 이상·흔한 비밀번호 거부로 약한 비밀번호를 줄였을 뿐이라, 약한 비밀번호를 쓴 계정은 반복 시도로 뚫릴 수 있습니다.
2. **2차 인증이 없습니다.** 비밀번호가 한 번 새면 그 계정을 막을 두 번째 장치가 없습니다.
3. **비밀번호 재설정이 없습니다.** 이메일 등 복구 수단을 받지 않아서, 비밀번호를 잊으면 계정을 되찾을 수 없습니다(계정 삭제도 비밀번호가 필요). 복구 기능을 만들면 그것이 새 공격 통로가 되기 때문에 이번에는 만들지 않았습니다.
4. **보안 기록(감사 로그)이 없습니다.** 서버 로그에는 경로와 상태코드만 남고, "누가 몇 번 로그인에 실패했나", "누가 남의 자료를 건드리려 했나"를 따로 모으거나 알려 주지 않습니다. 공격이 있어도 알아채기 어렵습니다.
5. **가입 때 아이디가 이미 있는지 알려 줍니다.** "이미 사용 중인 아이디입니다"로 어떤 아이디가 있는지 알아낼 수 있습니다(계정 열거). 로그인 쪽 문구는 같게 맞췄지만 가입 쪽은 그렇지 못합니다.
6. **자료 번호가 1, 2, 3처럼 이어지는 숫자입니다.** 추측하기 쉽습니다. 지금은 소유자 확인(`owned_or_404`)이 막아 주지만, 방어가 그 한 곳에 의존하므로 새 API를 만들면서 그 호출을 빠뜨리면 바로 노출됩니다.
7. **"모든 기기에서 로그아웃" 버튼이 없습니다.** 다른 기기의 세션은 비밀번호를 바꾸거나 24시간이 지나야 끊깁니다.
8. **내용 보안 정책(CSP) 헤더가 없습니다.** 화면에 넣는 글은 모두 이스케이프하지만, 만에 하나 빠진 곳이 있어도 막아 주는 두 번째 방어선은 없습니다.
9. **(확인의 한계)** 위 기록은 로컬 개발 서버(HTTP)에서 받은 것이라 쿠키의 `Secure` 표시와 HTTPS 이동은 별도로 확인했습니다(배포 모드 gunicorn에서 HTTP→HTTPS 301, `Secure` 쿠키 확인). **배포한 실제 주소에서 같은 확인을 한 번 더 하고 결과를 적어야 합니다.** `[직접 작성]`

1. **어디로 가나요:** `[직접 작성: 배포 주소]` 를 시크릿 창에서 엽니다(첫 화면이 로그인 화면).
2. **세 단계 안에 무엇을 하나요:** ① "가입하기"로 새 계정을 만들고 계획을 하나 추가합니다 → ② "로그아웃"을 누릅니다 → ③ 주소 끝에 `/app/`을 직접 입력해 엽니다.
3. **무엇이 보이면 통과인가요:** 3단계에서 자료 대신 **로그인 화면**이 나오고, 다시 로그인하면 내가 만든 계획이 그대로 보입니다. (아이디만 맞고 비밀번호가 틀려도 "아이디 또는 비밀번호가 올바르지 않습니다."라고만 나옵니다.)
4. **안 될 때는 무엇이 보이나요:** 가입에서 "이미 사용 중인 아이디입니다."(아이디 중복) 또는 비밀번호 규칙 안내(8자 이상, 흔한 비밀번호 불가)가 보이고, 로그인에서는 "아이디 또는 비밀번호가 올바르지 않습니다."가 보입니다. 로그인 뒤 "불러오는 중..."에서 멈추면 서버가 깨어나는 중일 수 있으니 새로고침합니다.
